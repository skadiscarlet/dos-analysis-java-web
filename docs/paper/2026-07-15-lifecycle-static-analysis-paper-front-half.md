# 面向 Java Web 资源耗尽漏洞的生命周期静态分析

## 摘要

Java Web 服务在处理远程请求时需要解析输入、创建对象、维护跨请求状态，并将部分工作转交给异步组件。这些行为支撑了服务的正常功能，也建立了由外部需求驱动的资源增长路径。现有检测通常围绕对象分配、容器写入或任务提交等局部操作构造候选，难以统一判断攻击者控制的资源增长是否在完整生命周期中受到有效限制。本文提出一种面向 Java Web 及相邻 Java 网络服务的生命周期静态分析方法。该方法以外部入口 $E$、资源增长 $G(P)$、增长前限制 Guard、资源上界 Bound、后续同步或异步处理以及资源释放 $R(P)$ 为统一分析对象，并提出三条漏洞断言，分别刻画缺少有效 Guard 和 Bound 的直接增长、缺少有效 Bound 和 Release 的持续增长，以及 Release 存在但受到限制的持续增长。基于该模型，本文设计一套证据优先的混合分析方法：通过跨框架入口恢复、数据流与控制流分析、字段传播、异步注册建模和生命周期限制分析构建完整资源生命周期；对于自定义封装造成的局部语义缺口，使用受约束的大语言模型提出候选解释，并要求所有影响结论的语义关系均由确定性程序事实复核。本文进一步给出由独立真值构建、删失感知标注、基线比较、消融实验和受控动态验证组成的评价设计，将漏洞证据、有限性证据与未决执行状态分别建模，为后续原型评价提供可复现的实验协议。

**关键词：** Java Web；资源耗尽；拒绝服务；静态分析；资源生命周期；大语言模型

## 1 引言

拒绝服务攻击长期威胁互联网服务的可用性。不同于依赖大规模流量耗尽网络带宽的网络层攻击，应用层拒绝服务攻击通常利用少量、定向构造的请求消耗服务器的计算、内存、线程或连接资源，因而更难通过流量规模识别和阻断。 现有研究已经对正则表达式拒绝服务、算法复杂度攻击以及若干内存耗尽问题进行了系统分析。 然而，在 Java Web 应用及相邻 Java 网络服务中，外部输入如何经由框架处理、业务状态管理和异步执行转化为持续的活跃资源占用，仍缺少统一的刻画与检查方法。

这一问题源于服务器实现正常功能所采用的资源管理机制。Web 框架会在业务方法执行前接收并转换协议数据；应用会依据客户端参数创建对象、维护会话和连接状态；缓存与注册表会跨请求保存可复用信息；执行器、回调和协议状态机则会暂存尚未完成的工作。这些机制本身并非异常，但它们共同建立了一条从外部需求到服务端资源的增长路径。攻击者可以增大单次输入、反复触发操作、维持并发交互或扩展状态标识空间，使资源在释放前达到不可接受的规模。Java 的自动内存管理并不能消除此类威胁：只要对象仍被请求上下文、会话、队列、缓存或进程级组件合法引用，垃圾回收器便不会释放其占用。

现有静态检测大多从某一类局部程序事实出发。将数组分配、对象材料化、容器插入和任务提交视为资源增长点，可以获得具有较高覆盖率的候选；进一步证明外部输入到达这些操作，则可以排除一部分内部路径。针对数据保留型拒绝服务的研究还定位请求处理器和长生命周期对象，并追踪请求数据向长期状态的传播。[REF: DR.D] 这些工作为资源型 DoS 分析奠定了重要基础，但 Java Web 服务中的资源增长并不止于请求数据被某个长期对象保留。输入表示转换可以在请求内形成大规模材料化，短标量可以控制资源分配规模，异步生产与处理可以形成待处理工作，而同一局部限制还可能在多个会话、连接或业务状态之间被聚合。

资源增长的安全含义取决于它在完整生命周期中形成的净资源占用。增长前的准入限制、资源点自身的容量或预算，以及增长后的消费、关闭、过期和终止处理，共同决定外部需求能否持续转化为活跃资源。资源在不同持有者之间的移动不等于释放，局部容量也只有在覆盖实际聚合作用域时才构成有效边界。

本文据此把外部事件、资源增长、后续处理和释放组织为同一条生命周期，并区分三类失界情形：增长前缺少有效准入限制且资源点无有效上界；可重复增长且不存在释放；以及虽存在释放但其触发、执行能力、时间窗口或覆盖范围不足以抵消增长。

据此，本文设计一套面向 Java Web 服务的生命周期静态分析方法。该方法首先恢复不同框架和协议中的外部入口，识别受外部输入控制的资源增长；随后围绕每个增长点构建资源从创建、持有、转移到释放的完整生命周期；在此基础上分析 Guard、Bound 和 Release 是否能够对相应资源形成有效限制，并依据三条断言生成可复核的漏洞证据。CodeQL、控制流图、跨过程数据流、字段传播和异步注册模型负责恢复确定性程序事实。大语言模型仅用于补充自定义封装和业务操作中的局部语义，其输出必须经过程序事实复核，不能直接产生漏洞判断。

本文定义可实现、可审计的分析方法及其评价协议，不据此作出工具精度、召回率或性能主张。本文的主要贡献如下：

- **生命周期问题建模。** 本文提出以 $E$、Guard、$G(P)$、Bound、同步或异步处理和 $R(P)$ 为核心的资源增长生命周期，将请求内直接增长与跨事件资源累积纳入统一分析框架。
- **生命周期静态分析方法。** 本文提出三条漏洞断言，并设计一套从外部增长识别、生命周期构建到限制分析的静态检查流程。该流程将大语言模型限制为可验证语义候选的生成器，使最终结论能够由程序事实复核。
- **可审计的评价设计。** 本文给出独立真值构建、删失感知标注、基线与消融比较、统计检验及受控动态验证相结合的评价方案，用于在原型完成后检验方法的有效性。

## 2 背景与威胁模型

### 2.1 Java Web 服务的请求处理

Java Web 服务为网络请求提供统一的接收、解析和调度环境。一个服务通常同时包含协议接入层、框架运行时、应用逻辑和异步基础设施。客户端通过 HTTP、WebSocket、RPC、消息协议或自定义网络协议向服务发送事件；框架根据注解、接口实现、路由表或显式注册关系选择处理入口，并完成请求体读取、参数绑定、对象转换、认证衔接和异常处理；应用逻辑随后访问业务状态、构造返回结果或发起后续处理。[REF: Java Web frameworks]

请求处理并不总是在一次调用栈中结束。为提高吞吐量或实现长连接协议，服务可以把工作提交给执行器，将数据附着到会话或连接，在 Future 和回调链中保存上下文，或者由定时任务和协议处理器继续推进状态。由此，资源的创建位置、持有位置和释放位置可能分别位于不同方法、线程和框架组件中。请求方法返回只能表明当前调用结束，不能说明由该请求产生的资源已经终止。[REF: asynchronous Java programming] [REF: event-driven server analysis]

Java 的对象可达性进一步扩大了这一差异。请求内创建的对象可以通过字段写入、集合插入、闭包捕获和任务提交逃逸当前作用域，并由 session、connection、cache、registry、executor、singleton 或其他长生命周期组件继续持有。对于线程、连接、direct buffer 和协议状态等资源，其实际生命周期还可能由框架或底层运行时管理。资源耗尽分析因此不能只考察局部变量作用域，而需要恢复资源在整个服务执行过程中的持有与转移关系。[REF: escape analysis] [REF: resource lifecycle analysis]

### 2.2 资源增长型拒绝服务

服务器处理外部输入时不可避免地增加资源占用。本文所称的资源增长操作，是指将外部需求转化为服务端活跃资源的程序行为。根据增长发生的代码位置和资源形态，这类操作可以概括为四组常见代码特征。

第一类是**输入材料化**。框架或应用将网络表示完整读取、解析、解码、解压或反序列化为内存对象，资源成本由输入大小、结构和表示转换共同决定。第二类是**直接资源分配**。应用根据请求参数创建数组、缓冲区、图像、线程、连接或其他具有显式容量的资源。第三类是**跨生命周期容器增长**。请求数据或派生状态被写入 map、list、cache、registry、session 或协议状态，并在请求结束后继续存活。第四类是**异步工作增长**。应用将任务、消息或回调提交给 queue、executor、scheduler、Future 或 reactive pipeline，使待处理工作在原始请求之外继续存在。

四类特征用于描述增长在程序中的表现形式，而非四种互斥的漏洞。同一输入可以先被材料化，再进入异步任务；一次协议事件也可以同时创建待决状态和回调。无论增长通过何种代码形式实现，其安全含义都取决于外部主体能否控制增长，以及生命周期中的限制机制能否使资源占用保持有限。

### 2.3 威胁模型与研究范围

本文考虑能够访问服务公开接口的远程或低信任主体。攻击者不需要获得操作系统权限、修改服务端代码或破坏底层运行时。其能够在接口和协议允许的范围内重复或并发发送请求、提交消息和维持连接，并控制相应 payload 的内容、大小、结构、重复次数和标识空间。对于具有多步交互的协议，攻击者还可以选择是否继续发送确认、轮询、重连、关闭或其他后继事件。[REF: web application threat model]

本文分析的资源包括 Java 堆内存、直接内存、跨请求容器状态、协议待决状态、异步任务、线程、连接以及能够从 Java 代码和框架结构中识别增长与释放关系的其他服务端资源。分析同时覆盖两类资源影响：其一，单次或并发请求在后续释放之前形成的直接资源峰值；其二，资源逃逸请求或跨越异步边界后，由多次外部事件形成的持续累积。

本文暂不把纯网络带宽耗尽、与资源生命周期无关的纯算法复杂度攻击、死循环和栈耗尽作为核心检测目标。对于由外部服务管理且无法从 Java 程序及其部署信息恢复生命周期的资源，本文也不作完整性保证。若计算或外部依赖直接影响资源释放过程，它们可以作为生命周期中的处理条件参与后续分析。

## 3 问题分析

### 3.1 资源增长生命周期

本文以一次外部事件所驱动的完整资源增长过程作为分析单位。该过程表示为：

$$
E \rightarrow [Guard] \rightarrow G(P)
\rightarrow \Pi
\rightarrow [R(P)].
$$

外部事件 $E$ 携带攻击者可控的 payload 进入服务。增长操作 $G$ 将该 payload 所表达的需求转化为资源点 $P$ 的占用。增长后的处理过程 $\Pi$ 可以在当前请求中同步执行，也可以经过任务提交、消息传递、回调注册或协议状态转移继续执行。Release $R$ 则表示处理过程中能够降低 $P$ 占用的操作。

资源点 $P$ 是共享同一聚合范围、容量或预算约束以及释放机制的资源单元集合；它可以对应请求处理期间的内存表示，也可以对应跨请求容器、任务队列、连接状态或其他长期资源。对同一资源点的多次增长可以在时间上重叠：一次增长尚未结束时，新的外部事件仍可触发后续增长。因而，资源点在任意时刻的活跃占用由此前已经发生、但尚未被释放抵消的增长共同决定。

Guard、Bound 和 Release 分别从生命周期的不同位置约束这一过程。Guard 位于增长前，决定外部需求能否进入增长路径；Bound 作用于资源点，决定资源能够增长到的最大规模；Release 位于增长后，通过消费、删除、关闭、完成或过期等行为抵消已经发生的增长。三类机制的共同作用决定攻击者驱动的资源需求是否能够被限制在服务可承受的范围内。

### 3.2 生命周期限制机制

Guard 表示增长发生前的准入限制。它可以约束请求主体、输入规模、请求数量、并发程度或决定增长成本的其他外部条件。有效 Guard 的宏观作用是减少攻击者能够施加的资源需求，或者在需求超过允许范围时阻止增长发生。

Bound 表示资源点能够达到的有效上界。它可以限制单次增长的规模、同时存活的资源单元数量或资源点的总体成本。Bound 既可以由资源结构自身的容量形成，也可以由配额、并发控制、拒绝策略和其他全局预算机制形成。只要 Bound 能够覆盖攻击者可触发的全部增长，重复外部事件也不能使资源点无限扩大。

Release 表示对已经发生的增长进行抵消的生命周期过程。同步计算结束、容器删除、任务消费、协议完成、连接终止和服务端过期都可以承担资源释放作用。Release 的效果不仅取决于它是否存在，还取决于它在增长过程中能够发挥的实际作用。其触发可能受外部交互控制，执行可能受到服务端处理能力限制，发生时间可能形成资源积累窗口，覆盖范围也可能小于增长所产生的资源。本文将这些情况统称为**受限 Release**。

Guard、Bound 和 Release 并非相互替代的代码模式，而是完整生命周期中的三种限制角色。不同资源增长可以由其中一种或多种机制共同约束。本文关注的是这些机制能否在外部事件持续发生的条件下共同限制资源占用，而不是某一类检查、容量或清理语句是否在源码中出现。

### 3.3 生命周期漏洞断言

基于上述生命周期，本文提出三条资源耗尽漏洞断言。设 $\operatorname{Accumulates}(E,G,P)$ 表示攻击者能够通过重复外部事件实施 $G$，且不同事件产生的资源占用能够在 $P$ 中同时存活。三条断言按持续增长优先的方式划分生命周期：满足跨事件累积条件的路径由断言二或断言三描述，其单次增长不再重复归入断言一。

**断言一：直接增长失界。** 若外部事件 $E$ 能够控制增长操作 $G$，而增长前不存在有效 Guard，资源点 $P$ 也不存在有效 Bound，且该生命周期未形成跨事件累积，则攻击者能够直接扩大资源占用。由于资源可能在 Release 执行之前达到不可接受的规模，后续 Release 不影响该断言。

$$
\operatorname{Controls}(E,G)
\land \neg \operatorname{EffectiveGuard}(E,G)
\land \neg \operatorname{EffectiveBound}(P)
\land \neg \operatorname{Accumulates}(E,G,P).
\tag{1}
$$

**断言二：无 Release 的持续增长。** 若不同外部事件产生的资源占用能够在 $P$ 中同时存活，资源点 $P$ 不存在有效 Bound，且生命周期中不存在能够抵消该增长的 Release，则资源占用可以随外部事件持续增加。

$$
\operatorname{Accumulates}(E,G,P)
\land \neg \operatorname{EffectiveBound}(P)
\land \neg \operatorname{ExistsRelease}(P).
\tag{2}
$$

**断言三：受限 Release 下的持续增长。** 若不同外部事件产生的资源占用能够在 $P$ 中同时存活，资源点 $P$ 不存在有效 Bound，生命周期中虽然存在 Release，但 Release 受到触发条件、执行能力、时间窗口或覆盖范围限制，因而不足以使 $P$ 的净占用保持有限，则资源占用可以持续增加。

$$
\operatorname{Accumulates}(E,G,P)
\land \neg \operatorname{EffectiveBound}(P)
\land \operatorname{ExistsRelease}(P)
\land \operatorname{InsufficientRelease}(E,G,P).
\tag{3}
$$

三条断言从生命周期的宏观结构描述资源耗尽成立的条件。断言二与断言三由 Release 是否存在区分；断言一仅覆盖未形成跨事件累积的直接增长。四类增长操作均可根据其生命周期特征映射到上述断言，而不需要为不同 API 或资源类型分别定义漏洞。

## 4 生命周期静态分析工具

### 4.1 方法概述

给定 Java Web 应用、依赖和默认部署信息，本文的方法以外部增长关系 $(E,G,P)$ 为分析单位。它首先证明攻击者控制的资源需求，随后恢复资源从创建、持有和转移到释放的关系，并分析 Guard、Bound 与 Release 是否共同形成有效限制。第 3 节的三条断言只使用已经得到程序证据支持的生命周期关系；关系缺失时，方法保留不确定性，而不以缺失证据替代安全或漏洞判断。

该流程维护以 $(E,G,P)$ 为索引的待证生命周期关系。入口恢复产生外部可达关系，增长识别产生资源需求与资源点关系，生命周期构建产生持有、转移和释放关系，限制分析则产生 Guard、Bound 与 Release 对这些关系的约束。静态分析主干将由 CodeQL、跨过程数据流、控制流、字段传播、调用关系、异步注册模型和配置恢复共同实现。对于固定模型不能解释的自定义封装，大语言模型只能提出带代码位置的待证关系，例如某一调用增加何种资源、某一字段是否形成长期持有，或某一 helper 是否降低同一资源点的占用。每类关系分别由调用与类型事实、数据流、控制流、异步注册边或默认配置复核；未被复核的关系不得进入漏洞断言或生命周期证书。

为使模型辅助过程可重放，每次调用都将保存规范化代码切片、提示模板、模型及版本、解码设置、原始结构化响应和内容哈希；模型或接口支持随机种子时，同时记录种子。重复分析优先读取该响应工件，再重新执行确定性复核，而不重新生成语义候选。响应工件缺失、哈希不一致或无法在既定模型版本下解释时，对应待证关系保持未决，不得进入生命周期证书。

### 4.2 外部资源增长识别

本阶段的目标是从目标程序中确定外部入口 $E$、增长操作 $G$ 与初始资源点 $P$。Java Web 应用的入口由框架而非普通调用关系决定。控制器、Servlet、过滤器、WebSocket 端点、Netty handler、RPC 服务、消息消费者和协议回调采用不同的签名与注册方式，并可能经过配置和框架适配层间接进入执行。若只搜索常见注解，分析会遗漏非标准入口；若从底层网络读取开始遍历，又会引入大量框架内部路径。工具因此将结合处理签名和注册关系建立跨框架入口模型，在应用代码中恢复可由低信任事件触发的方法。

定位入口之后，分析需要确定输入所控制的资源需求。资源增长并不由 API 名称单独决定。一个容器写入可能增加新条目，也可能覆盖既有状态；一个分配操作可能使用固定常量，也可能由请求参数决定规模；一次任务提交可能对应固定工作，也可能位于由输入控制的循环中。基于这一代码特点，工具将以四类增长操作为高召回搜索范围，并进一步识别决定增长成本的表达式，包括材料化或解码规模、分配尺寸、容器 key 与 value、任务提交次数、输入控制的 fan-out 以及新资源所有者的创建。

工具将首先使用类型、调用和局部数据依赖提取候选增长。对于自定义 parser、wrapper、业务容器或资源创建 helper，固定 API 模型可能无法直接确定其资源作用。此时，工具可以向大语言模型提供入口签名、候选调用、相关参数和有限调用上下文，要求模型提出增长语义和待追踪表达式。随后，CodeQL 数据流和控制流将复核候选调用是否存在、输入是否实际影响增长，以及候选操作是否产生真实资源增量。不能由程序事实支持的模型解释不会进入后续分析。

在此基础上，工具以外部输入为源、以增长需求为汇执行跨过程数据流分析。不同增长类型使用不同的需求表达式：直接分配关注容量和尺寸，输入材料化关注进入解析或转换的数据，容器增长关注 key 与 value，异步工作关注提交次数和任务内容。只有当攻击者输入到达相应增长需求时，工具才建立 $E\rightarrow G(P)$ 关系。对于跨事件增长，分析还将判断重复触发是否产生新的资源单元，而不是反复覆盖同一状态。本阶段最终产生外部可达、受输入控制且具有明确资源语义的增长候选。

### 4.3 完整资源生命周期构建

资源增长发生后，工具需要恢复资源的持有位置、存活范围和后续释放。Java 对象的活跃范围通常不同于创建它的方法作用域。对象可以通过字段写入进入会话、连接、缓存、注册表或单例组件，也可以通过任务提交和闭包捕获转移给执行器或回调链。由此，同一资源的创建、使用和释放可能分散在多个方法、线程和框架事件中。

工具将以增长点为起点，沿对象构造、返回值、参数传递和字段写入恢复资源载体。对容器和协议状态，分析将跟踪接收对象和用于标识资源单元的值；对异步任务，分析将跟踪 payload 从请求线程进入 queue、executor、Future 或回调对象的过程。字段传播和对象逃逸关系用于确定资源是在当前请求内存活，还是由 session、connection、application component 或 process-level component 跨事件持有。这样，工具能够把同一增长 API 在不同持有关系下产生的资源影响区分开来。

普通调用图不足以恢复异步生命周期。任务提交与工作函数之间、定时注册与清理函数之间、listener 安装与回调之间，以及协议事件与后继处理器之间，通常不存在直接调用边。工具因此将为常见执行器、调度器、Future、网络 listener、reactive operator 和协议处理机制建立异步注册模型，把提交、注册或调度位置连接到后续执行函数。只有能够由已建模注册关系到达的函数，才被纳入当前资源生命周期。动态装配、反射或未知框架行为无法解析时，工具保留该路径的不确定性。

在构建生命周期时，工具还需区分资源释放与资源转移。从 queue 中取出任务可以降低队列长度，但任务及其 payload 可能继续由工作线程或下游状态持有；请求返回可以结束局部调用，却不能终止已经提交的异步资源。因此，工具将沿资源传播继续追踪候选 Release 的后继持有关系，只有使当前资源点净占用下降的操作才被视为 Release。

自定义业务方法可能隐藏资源保留、转移或释放语义。针对这类局部缺口，工具将向大语言模型提供围绕单个增长点构造的有界代码切片，其中包含已确认的数据流、字段传播、调用和异步注册关系。模型只需提出某个 helper 可能承担的生命周期角色以及需要验证的代码关系。工具随后以对应的静态查询复核该关系，确保完整生命周期的结构仍由可重放证据决定。

### 4.4 生命周期限制分析

在完整生命周期上，工具将依次分析增长前的 Guard、资源点上的 Bound 以及增长后的 Release。该阶段的核心目标不是寻找具有特定名称的限制代码，而是判断限制是否作用于当前增长所对应的资源需求。

对于 Guard，工具从增长点反向搜索权限检查、长度比较、数值裁剪、并发控制和其他准入条件，并使用控制流分析判断这些条件是否位于增长之前。一个检查只有在超限分支阻止执行到达 $G(P)$ 时，才能限制相应增长。由于外部数据可能在框架内部经历聚合、解码和对象转换，工具还将比较 Guard 检查的输入表示与增长实际消耗的资源表示，避免把不同处理阶段的数值约束视为同一限制。配置恢复用于确定 Guard 所依赖的默认值、profile 和覆盖关系。

对于 Bound，工具以资源点为中心恢复容量、配额、并发许可、驱逐策略和拒绝行为。容器或队列具有有限构造参数，并不自动说明新增资源会在达到容量时被阻止；工具还需检查满载分支以及调用者对失败结果的处理。对于按会话、连接或业务标识划分的局部 Bound，分析将继续恢复相应资源范围，判断这些局部边界能否共同限制程序中的总体资源。工具还将区分结构性有界与预算内有界：前者表示增长不能无限继续，后者还需要结合单项资源成本和部署预算确定有限上界是否可承受。

对于 Release，工具从生命周期中提取删除、消费、关闭、完成、取消、驱逐、过期和资源特定释放操作，并确认它们是否使同一资源点的净占用下降。同步 Release 需要结合正常返回、异常和提前退出路径进行分析；异步 Release 则需要结合已恢复的注册边和后续处理函数。对涉及状态标识的资源，工具还需验证增长和释放是否对应同一类资源单元。

在确认 Release 存在后，工具进一步分析其限制。协议确认、轮询、重连和主动关闭等 Release 可能依赖后续外部事件；工作线程和回调的 Release 可能受到有限处理能力或阻塞操作影响；定时清理可能只在一定窗口后发生；Release 也可能只覆盖部分终止路径或部分增长。工具将通过事件来源、控制流、阻塞调用、时间条件、注册关系和资源传播识别这些结构。若 Release 的充分性依赖无法从静态程序中确定的实际请求率、执行速率或部署调度，工具不会用模型猜测该关系，而是保留相应的不确定性并生成后续观测需求。

自定义清理和状态转换缺少统一 API。大语言模型在本阶段可以帮助提出某个 helper 是否降低资源占用、一次操作可能覆盖多少资源单元，或某个业务条件属于哪类生命周期限制。模型输入仅包含当前生命周期和已经恢复的程序事实；模型输出必须指向具体代码位置，并由接收对象、数据流、控制流、注册或配置事实复核。未经复核的自然语言判断不能作为漏洞证据。

### 4.5 漏洞判定与证据生成

完成生命周期限制分析后，工具按第 3.3 节的分类顺序组织判断。分析首先确认不同外部事件产生的资源占用能否在同一资源点中同时存活；若不存在 Release，则应用断言二；若 Release 存在但不足以使净占用保持有限，则应用断言三；仅在未形成跨事件累积时，才依据攻击者对增长的控制、增长前 Guard 和资源 Bound 判断断言一。调用关系、配置、异步语义或资源对应关系不足时，工具保留不确定结论，而不把缺失证据解释为安全或漏洞。

为使判断可供审查，工具将为每个候选生成生命周期证书。证书围绕一条外部增长关系记录：入口如何触发增长，攻击者输入控制何种资源需求，资源如何在同步或异步执行中被持有和转移，哪些 Guard、Bound 和 Release 参与限制，以及三条断言中的哪些条件得到程序证据支持。证书同时记录分析依赖的配置与部署假设，以及尚未闭合的生命周期关系。

生命周期证书也作为静态分析与后续验证之间的接口。对于需要动态确认的路径，工具根据未决关系生成定向观测需求，例如资源点活跃规模、增长和释放次数、长期组件数量、异步处理延迟和服务可用性。该设计使静态分析、人工复核和受控动态验证围绕同一条资源生命周期进行，而不是分别产生无法对应的告警、解释和实验结果。

## 5 实验设计

### 5.1 研究问题

本文计划围绕以下研究问题评价生命周期静态分析方法。

- **RQ1：生命周期分析能否提高资源耗尽漏洞的识别能力？** 比较完整方法与仅识别增长、仅证明 $E\rightarrow G$ 的方法，评价生命周期信息对漏洞候选区分的贡献。
- **RQ2：三条生命周期断言中的不同因素是否必要？** 分别考察 Guard、Bound、Release、异步注册、资源对应关系和作用域分析对结果的影响。
- **RQ3：受约束的大语言模型能否补充确定性分析？** 比较纯规则、仅模型判断和“模型提议、静态复核”三种设置，评价语义候选召回、证据支持率、稳定性和人工审查成本。
- **RQ4：删失感知的真值设计是否影响评价结论？** 比较将有限未故障运行视为普通负例与将其作为独立执行状态两种设置，分析评价指标和方法排序的变化。
- **RQ5：工具产生的生命周期证据是否具有可复核性？** 评价证书完整性、独立审查通过率、分析时间以及从静态候选到动态验证的人工成本。

### 5.2 数据集与真值构建

评价以“项目版本、默认部署、外部入口和资源生命周期”作为基本分析单元。数据集将覆盖不同 Java Web 框架、协议入口、资源类型和增长方式，并保证源码、依赖、配置与部署信息足以支持独立审查。为避免同一项目中的框架封装和配置模式同时进入训练与测试，数据划分以项目为单位完成，并在规则、提示词和阈值调整前冻结。

真值构建区分安全证据与动态执行状态。安全证据轴包含：经审查确认能够触发目标资源故障的 `CV`（Confirmed Vulnerable）、在明确配置和部署假设下具有可验证资源边界的 `VB`（Verified Bounded），以及证据不足的 `I`（Indeterminate）。动态执行轴包含：已观察资源增长但实验在故障或稳定状态前结束的 `DG`，有限探测未出现目标故障的 `DNF`，受环境、权限、路由、版本或业务前置条件阻断的 `BLK`，以及尚未运行的 `NR`。

两条轴相互独立。`DG`、`DNF`、`BLK` 和 `NR` 均不能自动作为安全负例；`VB` 必须由源码、配置、资源作用域和预算证据独立支持。标注过程将由至少两名评审者在不知道系统输出的条件下完成，第三名评审者负责仲裁分歧。系统生成的生命周期证书和模型解释不得作为真值证据。评价将报告原始一致率、机会校正的一致性统计量和仲裁比例。[REF: empirical software engineering annotation]

### 5.3 Baseline 与消融

评价将构建由弱到强的基线。`Growth-only` 基线只报告四类资源增长操作；`E→G` 基线进一步证明外部输入可达增长需求，但不分析完整生命周期；`Cleanup-proximity` 基线使用增长附近的检查、容量或清理代码作为限制信号；`Local-bound` 基线识别单个容器或资源的局部容量，但不分析跨作用域组合与异步 Release。若能够在相同分析单元和威胁模型下公平复现现有资源保留或资源耗尽检测工具，评价将把它们纳入外部基线。[REF: DR.D] [REF: resource leak analysis tools]

为分析各部分贡献，评价将设置以下消融：移除 Guard 分析、移除 Bound 与资源作用域分析、移除 Release 分析、移除异步注册模型、移除资源对应关系、移除配置恢复，以及移除大语言模型辅助。针对模型辅助，还将比较纯规则、仅模型判断、模型提议但不执行静态复核，以及完整的模型提议与确定性复核方案。所有基线和消融在冻结的项目级测试集上运行。

### 5.4 评价指标与统计方法

主分析在独立确认的 `CV` 与 `VB` 样本上报告漏洞识别 precision、recall、F1、balanced accuracy 和对有限路径的 specificity。其中，将 `CV` 判断为有界是最严重的错误，评价将单独报告 false-bounded rate。对于全部样本，评价还将报告不确定结论比例、selective coverage，以及不同动态执行状态上的输出分布。

生命周期证据的质量通过证书完整性和独立复核通过率衡量。人工成本包括单个样本的审查时间、仲裁成本和从静态结果构造动态验证所需时间。模型辅助部分还将报告候选语义召回、未经静态事实支持的 claim 比例、固定输入下的运行一致性、模型调用成本和 token 消耗。

统计分析以项目为聚类单位，使用 cluster bootstrap 计算 95% 置信区间。对同一批样本上的系统变体，采用配对检验比较分类结果或排名指标，并对多项消融比较执行预先指定的多重检验校正。主要指标、排除条件、样本划分和未知结论的处理方式将在测试集分析前冻结。[REF: statistical methods for empirical software engineering]

### 5.5 受控动态验证

动态验证用于补充静态生命周期证据，而不是替代静态判断。所有测试仅在隔离、授权且具有明确资源上限的本地或容器环境中执行。对于静态分析给出的高置信漏洞候选，验证构造与证书相对应的输入和事件序列，记录资源点的活跃规模、增长与释放次数、内存或线程使用、异步处理延迟以及服务可用性，并按照预先规定的故障与资源证据标准判断是否确认漏洞。

对于静态证据表明存在资源边界的路径，动态验证检查 Guard、容量、到期和 Release 是否在默认部署中按证书所述生效，并观察资源是否在工作负载下保持有限。对于依赖运行时处理能力的未决路径，验证重点测量增长和释放行为，而不预设静态阶段无法证明的速率关系。

有限时间内未出现目标故障只描述该次执行的观察结果。客户端超时、请求上限、环境阻断和未满足的业务条件也分别记录为执行状态，不能单独将静态候选重新标记为安全。通过使动态测量与生命周期证书共享同一资源点和限制关系，评价能够区分程序机制、部署假设和实验边界对结果的不同影响。
