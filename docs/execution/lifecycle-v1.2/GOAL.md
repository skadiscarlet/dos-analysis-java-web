## 0. 执行目标

请实际修改代码、运行验收、生成报告并完成 Git commit/push，不要只返回计划。基于已经完成的 v1.1 增量开发，不重新实现 caller/task 联合求解、两层包装调用或任务数 K+W 检查。

用户已经要求完成后 push。本轮代码、测试、文档和脱敏汇总的正常独立分支推送无需再次询问。真实访问权限、网络或依赖阻塞如实记录，不能绕过，也不能用模拟结果宣布完成。

4. 新状态文件使用 `docs/execution/lifecycle-v1.2/STATUS.md`，记录阶段、验收、真实命令、结果路径、阻塞和下一条动作。
5. 本轮修改 `resource-*` 的工程接入，不改变旧 P0 schema/tool 2.5/0.4.0 的结论协议，不自动启动旧 `full` 扫描或模型调用。

## 3. 阶段 A：唯一的性质发布接口与多资源输出

### 3.1 普通分析和评价必须得到同一组性质

检查 `invariants.py`、`commands.py`、`source_evaluation.py` 的性质生成路径。建立或复用一个由求解结果发布性质的共享接口，普通 CLI、评价、报告、回放都消费它。

每条性质至少记录：

```text
property_id
analysis_unit_id
resource_family_id 或 executor_id
dimension
scope
cut（请求出口、指定任务终止后等）
status
upper_bound / relation
assumptions
coverage_gaps / unknown_reasons
evidence_refs
```

字段可以沿用已有类型，不必为相同信息建立平行 schema。性质 ID 依据输入身份及其语义生成，不依赖 expected 标签、列表顺序或时间戳。

评价脚本只做三件事：选择已发布性质、与独立标签比较、计算指标。不得从 `property_states`、计数或 expected.cut 再自行生成一个普通 CLI 没有发布的 bounded/obligation_gap。

若现有公共后端已经提供等价检查，直接复用并删除重复分支；不要重新发明算法。缺少对应性质时输出 missing_property/unknown，不能把“找不到”解释为上界零。

### 3.2 支持一个单元中多个资源族

移除评价器“一单元恰好一个 family”假设。一个方法有多个分配、一个任务捕获多个对象、多个候选指向同一资源，均应能逐条输出。

输入可以用源码位置、精确符号或稳定 family ID 选择观察对象，但不能提供最终结论。同名方法或同行多操作用 AST/程序点身份区分，不能只按文件行号关联。

共享同一输入与分析单元的候选可复用计算，报告仍保留每条输入到性质的映射。不能将每个候选的重复副本计为独立资源、独立发现或独立实验。

### 3.3 保持性质范围

- `after_task_termination` 只说明到达该终止切面后的性质；不能推断任务最终一定完成。
- 请求返回时的状态、所有已提交任务终止后的状态和任意时刻的上界分别表达。
- 族/实例数量、显式关闭义务、任务数和字节数分别报告。
- 某个单元超预算或某条路径未覆盖，不能从已完成子集发布无条件全局 bounded。
- 同一个单元的无关资源能否保留结论，由实际依赖关系决定；不得为了提高覆盖随意忽略全局精度缺口。

验收：一个包含至少两个资源族的编译样例，在普通分析、完整评价和重放中给出相同的性质 ID、维度、范围和语义结果；修改 expected 标签只改变匹配统计，不改变任何分析结果。缺字段、歧义和未知反例不被静默丢弃。

## 4. 阶段 B：明确本地项目的接入与分母完整性

### 4.1 项目 manifest

沿用现有 CLI 命名风格，增加一个项目级离线入口，或为现有命令增加 project manifest 模式。本文中的示意名称不必照搬，但 README 必须写实际可执行命令。

清单内容至少包括：

| 字段 | 内容 |
| --- | --- |
| project_id | 稳定项目/模块身份 |
| source_root | 用户明确提供的本地源码位置 |
| revision/tree_hash | 实际版本；不把另一个 Git 工作树的 SHA 当输入版本 |
| database | 已有且匹配源码的 CodeQL database，或明确的本地编译配置 |
| selection | 精确方法集合或已有结构化检查单元清单 |
| dependency_scope | 纳入了哪些源码/依赖；未知依赖如何记录 |
| budgets | 单元和批次时间、状态、证据、磁盘预算 |
| output | 本轮独立结果目录 |

源码根目录可以与清单分离配置，提交仓库的清单不泄露用户本机敏感路径。不得自动下载、启动或探测项目涉及的服务。编译命令应来自明确的本地构建配置，仅完成离线编译所需步骤。

### 4.2 两种检查单元输入

必须支持：

1. **精确方法输入**：用户给出本地项目的方法集合，分析器自行提取分配、资源关系与任务。
2. **已有结构化候选导入**：复用仓库现有入口/增长事实中的源码位置、callable、分配位置与输入依赖引用。仅导入观测事实；`actual_reduction/effective_bound/static_vulnerable` 等旧判断不得成为新求解前提。

如果现有候选不能与资源分配、快照或作用域唯一对应，保留 `mapping_ambiguous/mapping_missing/stale_source`，不按字符串相似度强行配对。

此接入只连接静态检查输入。不能把它写成自主选择项目、构造漏洞触发链或执行动态验证的流程。

### 4.3 每个输入都有去向

项目结果必须保留完整台账：requested、mapped、extracted、analyzed、unknown、failed、skipped。状态以阶段维度表达，避免互相重叠的计数被误加。

至少能核对：

```text
请求的检查单元
  = 成功映射的单元 + 映射缺失/歧义/版本不符的单元

成功映射的单元
  = 完成分析的单元 + 提取失败的单元 + 分析失败/预算退出的单元
```

明确 skip 的理由；不支持的输入不能从分母消失。零结果不能自动标为安全或已证明受限。

按复用的 unit/family/source identity 去重运算，按原始输入 ID 保留报告。输入排序变化不得改变结果；同一项目内存在不同 executor/holder 时不能错误合并。

单元级超时可以隔离，继续独立单元。公共 CodeQL 查询失败会使所有依赖该查询的单元失效，不能为了继续批次而将部分原始事实冒充完整提取。完整批次状态为 partial 时应明确展示。

验收：同一清单混合正常输入、多资源单元、重复引用、缺失方法及过期位置，台账准确；方法模式与候选导入模式对同一资源得到相同性质。全流程不需要 expected 标签，也不需要 LLM。

## 5. 阶段 C：证据分片、预算与跨目录回放

这是实际规模问题，不开展额外通用安全框架建设。v1.1 已有权限、锁、原子写入和哈希设施，优先复用。

### 5.1 不再将所有推导展开进一个大 JSON

对 facts、求解记录、evidence 和评价结果中会随输入增长的大对象检查重复结构。采用按分析单元/性质的分片和稳定引用，保留一个小索引：

```text
run-index.json
units/<stable-id>/properties.json
units/<stable-id>/evidence-*.json
shared/<content-id>.json
summary.md
```

路径是建议，不要求移动无关代码。共享源码位置、契约和相同推导节点按稳定 ID 复用；单元状态、路径和任务身份不能因去重而丢失对应关系。

每个读取仍受原有大小约束。分片索引也需有明确预算；数据更多时分页索引，不把超大 JSON 转移到另一个文件。不能只提高 16 MiB 上限或删除支撑结论的证据。

同时约束解码后的内存及总证据预算；流式读取不能在末尾重新把所有分片合成一个无限大对象。单元内部状态爆炸仍返回预算退出，分片不应伪称解决了所有求解复杂度。

### 5.2 回放必须复算而且适合自动执行

- 索引绑定输入、工具、契约和必要分片的身份/哈希。
- 性质与证据身份使用源码树相对路径、内容和符号身份。source-root 与输出目录绝对路径仅作环境元数据；在源码相同的情况下重绑定根目录，不得改变性质 ID 或语义结论。
- 复制结果目录到新位置后，通过显式 source-root 重绑定核对相同源码，能重新验证、求解并比较语义结果，不依赖旧 `/tmp/lifecycle-v11-*`。
- 无法取得匹配源码时可以执行明确的完整性检查模式，但不能把它叫作完成语义重放。
- 缺失必要分片、错误引用、内容不一致或不可复算时返回非零退出码；不能仅写 `consistent=false` 后返回成功。
- 单元选择回放明确标为 partial/selected，不能冒充整个 run 已验证。
- 只有全部已声明必需分片发布完毕，最终索引才标记完整；进程中断不会留下看起来 complete 的批次。

旧 v1/v1.1 格式若可读取，保留对应 reader 或给出清晰版本错误；不要悄悄用新默认语义重解释旧结果。

### 5.3 有界规模测试

使用 v1.1 已编译案例的多个独立重命名副本/单元，构造固定的 1×、2×、4×规模组，只测试性能与交付，不称为独立项目或泛化数据。

记录 raw fact 数、状态数、性质数、总序列化字节、最大分片、运行时和峰值分析器内存。若状态数近似线性而证据反复展开导致超线性增长，应查清重复来源。

至少有一组测试在真实结果字节规模上超过旧单文件上限，仍能在保持单片限制下完成普通分析与完整重放。另测单元证据超预算，确认被准确报告且不影响独立单元。

不能通过只生成空引用、提高上限或不保存失败单元来通过。比例数据用于诊断，不为不同程序结构承诺一般线性复杂度。

## 6. 阶段 D：独立本地源码评价

### 6.1 选择清单与冻结

优先使用用户已经明确提供的本地项目清单；若已有明确的工作项目资料，先只读核对其源码版本和可编译模块。不得因某目录有数据库或 PoC 标签就自动将其纳入。

目标是至少两个独立存在的本地项目/模块、合计 6–10 个检查单元。不得把新创建的 fixture 重命名成“真实项目”。同一项目两个模块只能报告为两个模块，不能声称两个项目。

保留实际依赖、包装方法和调用关系。需要缩小编译范围时记录省略内容及其影响，不能删除不利分支或手工补齐资源关系。

清单选择与 oracle 标签分开：先固定输入版本、方法/资源选择、支持范围和模型配置，再运行分析。至少一个模块在规则冻结后评价；若根据它修改规则，它便不再属于该轮未参与开发的评价模块，须如实重新标记。

若缺少可用独立源码或构建依赖，继续完成阶段 A–C 与复用 fixture 的工程回归，生成接入清单模板、已尝试输入和具体阻塞。独立评价记 blocked，整轮 partial；不停止保存和推送已完成成果，不用新造样例冒充缺失资产。

### 6.2 分析内容与有限改进

从资源管理正确性和已知维护行为出发，包含同步跨方法、异步移交、多持有者或多个资源族，以及未知分派/配置的合理反例。输入范围内静态检查即可，不需要服务运行或耗尽资源的实验。

首先输出 v1.1 原支持范围在这些输入上的覆盖和 unknown 分布，再决定是否补足最多两类反复出现的低成本提取缺口。例如唯一局部别名或可解析常量配置，必须由源码数据流/契约验证。

新增规则需可迁移到独立反例，不按项目名、方法名、样例 ID 或期望标签特判。不得为了减少 unknown 而默认未知调用纯净、默认 close 不抛异常或忽略额外 writer。

本轮不强制降低某个 unknown 百分比，不要求检出指定数量的问题。可用性和正确性问题必须修复；超出声明语义的场景保留未知并明确下一步所需信息。

### 6.3 对照与标签

同一源码、同一检查单元和同一 raw facts 上运行完整模式及已有跨事件消融。完整和消融的结果由阶段 A 同一性质接口发布。

分别报告：构建成功率、输入映射率、资源/调用/任务关系覆盖、每个维度的确定性质比例、unknown 原因、分析成本、重复单元节省量。

有可靠独立标签时再报告性质符合度和错误；没有标签时只报告覆盖与待审结果。历史“发生过 OOM”的描述不能直接转换成本检查器的真值。

每个模式都展示同一个分母。不能只统计完成且给出确定结论的子集。人工 IR、源码 fixture、独立模块和压力规模副本分别列出。

如果独立模块没有出现传播增益，应报告零增益并分析原因，不把它当成必须通过修改样本消除的失败，也不能仍声称证明了外部有效性。

| `metrics.json` | 按数据来源分层的覆盖、未知、失败与成本 |
| `scaling.json` | 1×/2×/4×规模、最大分片与重放结果 |
| `gates.json` | H1–H6 状态及证据路径 |
| `run-manifest.json` | 实际代码/查询/输入/契约身份、配置和重跑方式 |
| `baseline-test-diff.json` | 同环境失败、错误和 skip 的测试 ID 差分 |

索引和分片复用阶段 C 的实际格式。提交可公开的紧凑汇总、清单与合成回归；不提交整个独立项目源码、数据库、原始 PoC、私有录制或大型运行日志。

若分片不可公开，HANDOFF 需列出本地持久结果位置和构建/重跑命令，明确后续仅从 GitHub 可审阅到什么。不能只有即将被清理的临时目录。

更新 README、CHANGELOG、语义和限制文档。旧版本能力表应明确标为历史，当前支持表只保留一份权威口径，避免读者同时看到互相矛盾的范围说明。保留旧固定报告不覆盖。

## 8. H1–H6 硬验收

| 门槛 | pass 条件 | 不能算作 pass |
| --- | --- | --- |
| H1 性质一致 | 普通分析/评价/重放发布相同性质，多资源逐条输出，oracle 变动不影响分析 | 评价脚本自行从状态生成新结论 |
| H2 项目接入 | 两类输入均可运行，分母完整，缺失/重复/歧义/失败正确处理 | 手工改报告或静默遗漏不支持单元 |
| H3 规模与重放 | 真实字节量超过旧单文件上限的结果分片后可重放，非一致结果非零退出 | 只提高阈值、仅完整性校验冒充语义重放 |
| H4 独立源码 | 至少两个独立已有模块完成实际提取分析或明确范围内性质检查，并保留完整台账 | 用新的 fixture 或压力副本冒充独立模块 |
| H5 诚实评价 | 同事实对照、分层分母、unknown/失败/零增益准确报告，规则冻结记录可追溯 | 把期望 unknown 匹配当检出、改标签凑指标 |
| H6 可审阅交付 | 文档、清单、失败 ID 比较、版本关系、重跑命令与待提交内容核查完备 | 只给总通过数或 reviewer Ready |

H4 不要求所有方法都给出确定结论，但必须真实运行、解释覆盖和未决原因；若全部单位都在映射或构建阶段失败，H4 不能 pass。

`implementation_status=complete` 要求 H1–H6 全部 pass。缺少独立输入可将 A–C 标记完成，但整轮为 partial。不得降低门槛、伪造数据或无限等待资产。

工程完成不等于论文实验充分；两个模块只支持初步适用性判断，不承诺跨项目准确率、所有协议覆盖或一般性资源耗尽判定。

## 9. Git 提交、push 与最终交接

1. 在正确 remote 的独立分支上工作。审阅 `git status --short`、本轮 diff 和 `git diff --check`；只暂存明确的本轮文件，不无差别 `git add .`。
2. 排除凭据、私有请求、数据库、大型日志及用户无关改动。使用已有 Git 身份；缺失时如实报告，不能虚构身份。
3. 完成代码和报告后提交。本地报告记录 `implementation_status` 及 `delivery_state_at_commit=ready_for_push/blocked`，不提前声明自己的提交已经在远端验证。
4. 已确认目标 remote 为 origin 时，独立执行并检查以下命令；实际 remote 不同时使用已确认名称，不改写 origin：

```bash
lifecycle_remote=origin
lifecycle_branch=$(git branch --show-current)
git check-ref-format --branch "$lifecycle_branch"
git rev-parse --verify HEAD
git push --set-upstream "$lifecycle_remote" "$lifecycle_branch"
git ls-remote --heads "$lifecycle_remote" "refs/heads/$lifecycle_branch"
```

5. push 成功且远端分支 SHA 与本地 HEAD 完全一致，才写 `push_status=verified`。非快进先检查差异，可用唯一新分支，不 force、不覆盖其他工作。
6. 即使整轮 partial，也推送完整的已完成成果和准确阻塞说明。真实权限/网络拒绝则保留本地提交并给出重试命令，不绕过，不虚报成功。

交接文件使用 `docs/execution/lifecycle-v1.2/HANDOFF.md`，开头必须包含：

```text
implementation_status: complete / partial / blocked
delivery_state_at_commit: ready_for_push / blocked
actual_base_commit: 实际值
branch: 实际值
H1–H6: 每项状态及证据路径
new_capabilities: 与 v1.1 相比实际新增什么
source_inputs: 独立项目/模块与 fixture 分开计数
property_consistency: 普通分析、评价、重放的一致性
scaling_and_replay: 最大分片、总证据、复算与退出码结果
evaluation: 分母、unknown、失败、对照和是否存在增益
remaining_gaps: 具体未完成内容
reproduce: 实际可执行命令与依赖
next_action: 仍需处理的下一条具体动作
```

报告使用分析时实际实现身份：记录已提交实现的 commit；运行时若有未提交实现改动，还需记录实际加载源码和查询的 tree/content hashes 及 dirty 状态，不能只用运行前 HEAD 冒充被测版本。提交自身不包含自己的最终 SHA。结束回复根据实际结果给出 `push_status`，只有实现 complete 且推送 verified，整个 `iteration_status` 才为 complete。

结束回复给用户：状态、H1–H6、核心结果、未完成项、分支、完整提交 SHA，以及固定提交下的 commit/HANDOFF/summary 链接。用户把链接发回后，后续会话可在具备仓库权限时读取；push 本身不会自动触发后续会话。
