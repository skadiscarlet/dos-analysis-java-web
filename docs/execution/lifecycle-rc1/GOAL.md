## 3. 工作包 A：让固定输入正确进入工具

### A1. 显式区分源码身份与提取范围

当前 commands._verify_database_source_snapshot 要求 live Java 文件集合与 src.zip 完全相等。保留“被分析字节必须对应 DB”的要求，同时把以下对象分开表示：

- 原始冻结源码树及逐文件 hash；
- DB 实际归档并参与提取的文件及 hash；
- 未归档文件、原因与对所选方法/依赖的影响；
- 本轮实际选择的方法和已覆盖的源码范围。

优先采用现有 manifest 的最小扩展。每个已归档、被使用的文件仍须与冻结原字节匹配；所选方法所在文件必须确实被提取。不能用“两个集合取交集”静默接受未知缺失。

对于注释占位、无 Java 声明的文件，用解析器或提取器信息说明其不贡献所选程序语义，保留原文件和 hash，不依赖文件名猜测。含声明但未提取的文件必须产生缺口；无法界定影响时不发布依赖它的确定性质。build-mode=none 仍不能声称完整编译或依赖解析成功。

如果已有 DB 的实际输入不能可靠绑定，按冻结源码新建 DB；不得改源码、伪造 src.zip 或覆盖原 DB。本轮范围限于已选择的模块，不设计通用多仓库构建系统。

验收：注释占位不会再导致无关已提取方法整批失败；已归档文件字节不符仍失败；所选方法文件缺失不能被接受为已覆盖。

### A2. 修复 8,885 行结果的接入

先检查 CodeQL 运行器、decode_bqrs_json/decode_rows 和 _codeql_facts 的预算位置；当前 entry_methods 在适配阶段使用，不会避免先解码整份结果。

在下列方案中选最小、可验证的一种，不要求全部实现：

- 生命周期查询采用有上限的专用行数/字节预算，能接收已观测完整结果；
- 在查询侧按精确方法及必要依赖闭包选择；
- 使用工具实际支持的有界分块/分页。

对于当前 8,885 行，允许以测量为依据提高生命周期专用传输额度；这与无界增大 solver 迭代数不同。不全局解除解码、字符串、输出或内存限制，不强迫为此建立通用分页平台。原有单片读取上限与新传输额度分别说明。

若做筛选，必须保留支持范围内所需的 callee、回调、构造参数、字段写入和 CFG 关系；被排除依赖影响结论时显式 unknown。若分块，校验完整性及跨块关联，禁止截取前 N 行当完整输入。

恢复 common-core 的原完整模块源码范围，仍使用原来的三个方法选择。保留 v1.2 缩包尝试作历史记录，报告输入范围变化；不要重新缩包通过验收。

验收：完整结果实际接入；不超过预算时无静默丢行，超限有准确诊断。将九输入和已有合成源码上选中单元的性质作一致性检查，不把提高行数本身算分析增益。

### A3. 让方法身份与资源识别分别可观察

当前 project._execute 用 extracted.units 是否存在判断 method_has_no_extracted_resource。增加最小的 callable inventory 或等价身份记录，使所选方法即使零个资源事实也能被定位。

至少区分：

- method_resolved：方法身份及源码位置找到；
- method_missing / ambiguous / source_mismatch：真正的定位失败；
- resource_unmodeled：方法找到，但存在当前无法建模的相关调用或资源行为；
- no_modeled_resource：当前提取规则没有产生资源族，附规则范围；不表示不存在资源；
- analyzed / budget_exit / extraction_failed：执行结果，独立于性质的 bounded/unknown 等状态。

字段名可以沿用现有规范，不必照抄。已知四条不能仅换成 success；必须给出方法解析证据、零资源事实原因，以及是否有外部依赖缺失。已有提取覆盖明确但接线丢失的事实应修复；超出当前模型的库方法保留 resource_unmodeled，不为四个方法分别硬编码结论。

验收：九条请求均有可解释的阶段记录；重复请求不增加计算，但仍保留原始分母。没有资源性质的请求不计入“已求解资源单元”，不能发布上界零。

## 4. 工作包 B：给循环求解加入真实收敛

先用合成最小程序复现问题，再在冻结的本地静态输入上检查同类原因。当前 solver 以 control、完整 ResourceState 和已走边集合做精确去重；merge_states 主要用于报告快照。create 每次增加累计 allocation_counts，即使每轮资源均被释放，也可产生持续不同的状态。这是需要修复的算法结构，不只是日志或超时参数。

实现一个有限范围的抽象不动点处理：

1. 在循环 SCC 的选定入口，按保留必要分支/任务阶段/实例信息的抽象配置记录已到达状态。
2. 实现并使用明确的抽象包含关系；新状态已被覆盖时停止重复入队。对可能无限增长的数值分量采用有限延迟 widening 或等价有限抽象。
3. 区分累计历史分配与当前持有、未关闭义务、峰值。累计分配无界不能污染已经独立证明的有限存活上界。
4. 谨慎处理重复分配位置：同位置的历史实例不等于当前实例。只有证明此前实例不再持有且相关义务已消除，才能保留下一次迭代的 recent 精度；否则使用摘要实例和弱更新。
5. 保留决定 release/drop 有效性的关系。互斥路径分别关闭不同实例，不能通过合并证据推出两个都关闭。任务阶段不能随意合并。
6. 证据和执行状态分离到必要程度，重复 evidence ID 不触发新求解。抽象推导记录为抽象推导，不伪装成一条具体可执行路径。现有 trace 已去重，不为不存在的“无限 append”问题另建系统。
7. 保留时间/状态预算兜底。widening 得到无穷上界只说明未证有限，不能作为结构性无界增长或漏洞证据。超出支持形式仍可 unknown，但应说明是精度限制还是运行未完成。

至少用以下三个合成源码回归验证，经真实提取进入主求解：

| 回归 | 验收要点 |
| --- | --- |
| 每轮完整 create/retain/release/drop，可退出 | 默认预算内收敛；在精确配对且无逃逸的已支持模型下，出口义务零，存活峰值一；历史分配数可无有限上界 |
| 每轮创建并保留新资源，可退出 | 默认预算内收敛；不发布有限持有上界，不因 widening 单独发布已证明累积 |
| 两实例经互斥分支分别关闭一个，再经过无效应循环退出 | 不误判全部关闭；保持一个未关闭实例的可能性，重复运行输出稳定 |

对相同冻结输入报告修复前后 solver steps、抽象配置数、widening/subsumption 次数、耗时及 peak RSS。证据体积作为辅助指标，不重新做整套规模平台。预算翻倍只能作为有针对性的诊断，不能充当收敛修复。

验收目标：当前已观测的循环单元在固定预算内形成完整抽象结果与语义回放；外部调用未建模仍可让性质为 unknown。若仍预算退出，报告剩余状态增长原因，R3 不通过，不能将 terminated 强改为 true。

## 5. 工作包 C：修复已声明支持的跨调用异常传播

保持原十二例源码、选择和 oracle 文件不变，重跑普通性质发布路径。重点检查 s2-task-only、s2-field-holder。

需要追踪：精确已建模 callee 内的 execute 拒绝/抛出，经包装方法的异常出口回到 caller，caller 的 catch/finally 和终止切面是否真实进入事件系统。传播的持有状态必须使用已有实例身份及路径条件。

- 已接纳、拒绝、正常完成、异常完成分别建模；拒绝路径没有成功派发，不得虚构任务 capture。
- 包装调用的异常返回不能被当作正常完成或任务终止。
- 使用现有受支持的精确调用深度，不同时扩到一般动态分派。
- 性质仍由唯一 properties 接口发布，评价器不依据 expected 或原始计数补 bound。
- 添加必要的异常路径合成反例，证明遗漏 caller cleanup 和额外持有者会改变结果；不写只镜像实现结构的测试。

验收：两个历史缺口由真实静态关系消除，原支持语义恢复，普通分析/评价/回放一致。如果独立核查发现原 oracle 本身不成立，保留原记录并给出明确的 oracle_disputed 解释；不得静默改期望以追求 12/12。未解决的真实语义回归不能只通过改为 expected unknown 消除。

本轮不承诺补齐所有库工厂、序列化与反序列化效果。如果明确的返回持有转移只需复用已有可信静态摘要即可修通，可以一并修接线；没有精确调用/资源绑定时保持未知。不得把“返回给 caller”当作释放。

没有独立 oracle 时只报告覆盖、完成率、未知原因和模型差异；不要把旧 OOM 记录当静态性质标签，不计算准确率/召回率。未来确有独立正例标签时，unknown 和工程失败都应计入全流程未检出分母。

### D2. 两层结果，禁止混用

工程发布状态使用：

- rc_ready：下面 R1–R6 通过，可冻结为受支持范围的实验版本；
- partial：仍有工程阻塞或未解决的关键回归，推送已完成工作和准确原因。

另设 research_evidence：

- observed：在有独立核查的性质与对照中观察到相应增益，并列出证据；不能凭运行成功填此值；
- unvalidated：仍缺独立正确性/增益证据，包括全 unknown、没有相关传播关系或没有 oracle。

rc_ready 可以与 research_evidence=unvalidated 同时成立，其含义是“工程版本可以开始覆盖与有效性实验”，不是“论文方法已被证实有效”。若独立结果仍零确定性质，明确写出，不能称完整漏洞检测工具或 paper-ready。

| R6 交付 | 相关回归通过，最终一次必要的同环境失败 ID 比较无未解释新增问题；文档、复跑命令、代码身份和正常推送可核对 |

R5 只是运行门槛，不等于检出、完整项目覆盖或生命周期收益。不得为了 R5 新找输入，也不得把 no_modeled_resource 计成非空资源单元。

最终全仓测试若被历史资产/环境问题阻塞，用同环境 baseline 的失败 ID 作比较，不以失败数量相同替代 ID 检查。已有同环境证据足够时复用；无需每个工作包跑全仓。新失败或新跳过必须解释，必要门槛的 skipped 不能算 passed。

若某项仍失败，完成其他已授权工作、记录具体失败后推送 partial；不要编造通过，也不要自动开始 RC2 或扩展新研究方向。本轮目标不允许靠降低门槛满足。

## 8. Git commit、push 和远端核验

先检查实际变更，只暂存本轮明确拥有的代码、测试、文档和紧凑报告。不要执行无差别 git add .；不包含用户无关修改或原始资产。完成实现提交和报告提交，必要时可合并成经准确 hash 绑定的提交。

在确认 origin 正是本项目、当前是本任务分支且变更已经正确提交后，实际执行：

```bash
set -euo pipefail

task_branch="$(git branch --show-current)"
test -n "$task_branch"
case "$task_branch" in
  codex/resource-lifecycle-rc1-*) ;;
  *) echo "当前分支不是本轮 RC1 分支，请先检查工作区。" >&2; exit 1 ;;
esac

git diff --check
git status --short
git push --set-upstream origin "$task_branch"

task_head="$(git rev-parse HEAD)"
task_remote_head="$(git ls-remote --exit-code origin "refs/heads/$task_branch" | cut -f1)"
test "$task_head" = "$task_remote_head"
printf 'push_status=verified\nbranch=%s\ncommit=%s\n' "$task_branch" "$task_head"
```

不要 force push、改写他人提交或自动合并默认分支。若远端存在新提交，先检查差异并正常协调；不能删除远端规避冲突。认证/网络失败如实报告，保留可重试命令和本地提交，不能写已推送。

最终回复必须包含实际分支、40 位 SHA、push_status、基于该 SHA 的 HANDOFF 和 summary 链接，以及 R1–R6、九输入各阶段计数、确定性质/增益、remaining gaps。partial 也交付已完成且可审阅的工作。

## 9. RC 后立即开始的实验工作

本节是下一阶段建议，不属于本次 /goal 的执行范围。本轮只在 HANDOFF 留下实验接续清单；完成第 8 节推送核验后结束，不自动添加输入、运行新实验或启动下一版本。

RC1 结束后，不默认继续堆功能。固定版本、规则和预算，同时开始：

1. 冻结真实输入总体、去重单位及独立标注规范，把当前九方法标为开发集；准备未参与修复的评价输入。已有 PoC 记录仅作为历史材料，缺陷性质与标签需要独立核对，本任务不运行复现。
2. 按冻结入口/增长候选比较 full 与生命周期消融，分别报告覆盖、工程失败、unknown、确定结果和成本。是否有相关跨调用/异步关系必须可见。
3. 在支持范围匹配后组织强基线和真实反例评价，不把合成源码当独立项目。
4. 仅对实验暴露的实现缺陷修补并记录版本变化；改变语义规则后受影响样本转为开发集，重新保留独立评价。新增框架、live LLM、通用总字节证明进入后续范围，不拖延既定实验。

本轮结束应回答三个不同问题：工具能否稳定运行？支持范围内是否算对？统一生命周期关系在独立输入上是否带来收益？分别用工程测试、性质核查和实验对照回答，不互相替代。
