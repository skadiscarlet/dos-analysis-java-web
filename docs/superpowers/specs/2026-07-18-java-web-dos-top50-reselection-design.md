# Java Web DoS Top-50 重选与 CodeQL 建库设计

## 1. 背景与目标

当前本地 `frameworks/applications/` 下有 183 个 Java Web 项目源码，其中 182 个具有包含 `codeql-database.yml` 的现有 CodeQL 数据库。旧清单 `frameworks/2026-07-04-github-java-web-app-top50.md` 的筛选精度不足：它过度依赖 GitHub stars 和宽泛的 Web/server 信号，不能充分证明默认部署入口、低权限可达性或具体资源耗尽机制。

本轮工作重新选择恰好 50 个高质量 Java Web server 型项目，替换旧 Top-50 清单中的绝大多数条目，并为最终 50 项准备可验证的 Java CodeQL 数据库。

本轮采用非破坏策略：只替换当前使用的清单和机器可读元数据，不删除、移动或覆盖任何已有源码、数据库或历史结果。

## 2. 验收指标

最终结果必须同时满足：

1. 新主清单恰好包含 50 个项目。
2. 与旧 Top-50 重合不超过 10 项。
3. 至少 17 项不在工作开始时的 183 项本地源码快照中，并完成新下载和 CodeQL 建库。
4. 每个项目的默认部署形态提供公开 HTTP、WebSocket 或 gRPC server 入口。
5. 项目可以无需外部依赖，也可以需要 1–3 个依赖项。
6. 可以要求首次初始化和登录，但匿名用户或普通低权限用户必须能触达相关服务功能；仅管理员、运维、内部或开发测试入口不满足要求。
7. 每个项目必须关联至少一个具体资源耗尽机制，而不是只凭项目类别、语言或 Web 属性推测。
8. 最终 50 项均具有通过验证的 Java CodeQL 数据库。
9. 所有旧源码和数据库原地保留。

## 3. 范围与排除项

### 3.1 纳入范围

优先考虑具有真实 server 产品形态和明确默认部署文档的 Java 项目，包括：

- Spring Boot、Servlet、Netty 等 Java server 应用；
- 自托管协作、文件处理、媒体、搜索前端、代理、网关、监控、调度或自动化平台；
- WebSocket 会话、订阅、广播、房间或实时消息服务；
- gRPC API server、streaming server 或控制面；
- 暴露上传、解压、导入、转换、批处理、查询、正则、模板、报表等高放大功能的应用。

### 3.2 排除范围

默认排除：

- 纯 SDK、库、客户端、示例、教程或基准项目；
- 只有管理面、运维面、内部面、开发测试面或默认关闭的可选入口；
- 必须修改默认配置才能暴露目标服务面的项目；
- 依赖超过三个外部组件才能形成基本部署的项目；
- 只有管理员或 operator 能触达相关功能的项目；
- fork、镜像、更名仓库或同一产品的重复实现；
- 正常核心职责就是持续承载数据增长的数据库、搜索引擎、时序数据库、图数据库、消息日志和协调存储等基础设施；
- 只有普通响应变大、正常日志增长、普通持久化增长或小型有界缓存的项目；
- 停止维护、官方部署证据不足、仓库不可获取或无法形成可信 CodeQL 提取的项目。

## 4. 总体方案

采用证据优先的两阶段漏斗，并将影响力优先和 DoS 模式优先作为并行发现通道。

```text
GitHub 候选发现
  ├─ 影响力优先通道
  └─ DoS 模式优先通道
          ↓
候选归一化与去重
  ├─ 当前 183 项快照
  ├─ 旧 Top-50
  └─ fork、镜像、更名及候选间重复
          ↓
默认部署入口核验
          ↓
资源耗尽相关性评分
          ↓
影响力与维护状态评分
          ↓
构建可行性预审
          ↓
独立负面审查
          ↓
50 项主清单 + 至少 15 项有序候补池
          ↓
下载所有本地缺失项目（至少 17 项）
          ↓
逐项目 CodeQL 建库与验证
          ↓
失败时仅从已完整审核的候补池递补
```

### 4.1 第一阶段：广泛发现

从 GitHub 发现约 150–250 个候选。影响力优先通道关注 stars、forks、发布、贡献者和生态采用；DoS 模式优先通道关注潜在高放大服务功能。两个通道的结果统一归一化、去重并进入同一证据审查流程。

### 4.2 第二阶段：证据审查

逐项核验默认部署入口、依赖数量、权限模型、具体资源耗尽机制、影响力、维护状态和 CodeQL 构建可行性。完成评分和负面审查后形成 50 项主清单与至少 15 项已完整审核的有序候补池。

## 5. 每项目证据契约

每个主清单和候补项目至少记录：

- GitHub slug 和规范 URL；
- 默认分支和筛选时固定 commit；
- stars、forks、最近发布或最近提交时间；
- 项目类型与主要真实用途；
- 官方默认启动或部署命令；
- 默认公开协议：HTTP、WebSocket 或 gRPC；
- 默认监听地址和端口证据；
- 所需外部依赖及数量；
- 匿名或普通低权限用户的可达功能；
- 具体潜在资源耗尽机制；
- 主要入选证据与反证；
- 初始 183 项快照中是否已有源码；
- 是否属于旧 Top-50；
- 是否已有 CodeQL 数据库；
- 构建工具、推荐 JDK、server 模块和 CodeQL 构建策略；
- 总分、分项分数、硬门槛结果、负面审查结果和最终状态；
- 所有关键事实的官方来源 URL。

仓库 README、官方部署文档、官方 Docker/Compose 配置、默认配置文件和仓库元数据可以作为证据。第三方文章只能作为发现线索，不能单独证明硬门槛。

## 6. 评分模型

每个候选按 100 分评估：

| 维度 | 分值 | 判断重点 |
|---|---:|---|
| 默认公开入口可信度 | 25 | 官方默认部署是否公开监听 HTTP/WebSocket/gRPC，是否无需开启可选组件 |
| 资源耗尽相关性 | 30 | 是否存在具体上传、解析、展开、批处理、查询、广播、排队、缓存或保留机制 |
| 低权限可达性 | 15 | 匿名或普通低权限用户能否触达相关服务功能 |
| 影响力与实际使用 | 15 | stars、forks、发布、贡献者和生态采用 |
| CodeQL 构建可行性 | 10 | Maven/Gradle 构建清晰度、JDK 可用性、模块规模和依赖可解析性 |
| 维护与证据质量 | 5 | 官方材料完整度与近期维护状态 |

主清单候选最低总分为 70，并设置不可由其他分数抵消的门槛：

- 默认公开入口可信度至少 18/25；
- 资源耗尽相关性至少 18/30；
- 低权限可达性至少 8/15。

影响力不设绝对淘汰线，但在其他证据接近时优先影响力和实际使用更多的项目。

## 7. 资源耗尽机制分类

候选必须至少对应一个具体机制：

- 单请求上传、多 part 或对象数量扩张；
- 压缩包、文档、媒体、模板或复杂格式解析；
- 大规模导入、导出、转换、扫描或批处理；
- 用户控制的正则、表达式、查询、过滤、排序或聚合；
- WebSocket 订阅、房间、广播、会话或消息积压；
- gRPC stream、并发任务、未完成请求或连接保留；
- 无界队列、延迟任务、后台工作项或 fan-out；
- 用户键控缓存、注册表、会话状态或内存索引；
- 外部请求代理、递归抓取、重试放大或连接池耗尽。

入选只表示具备高价值静态审查面，不表示项目已确认存在漏洞。后续安全结论仍需证明默认部署可达路径、攻击者控制、真实增长、生命周期和缺失有效边界。

## 8. 独立负面审查

每个拟入选项目都要接受一次以淘汰为目标的独立负面审查，至少检查：

- 服务是否实际只绑定 loopback；
- 入口是否属于管理、开发、测试或可选模块；
- 普通用户是否实际无权调用；
- 是否必须修改默认配置；
- 依赖是否超过三个；
- 潜在增长是否已有默认大小、数量、超时、配额或并发上限；
- 所谓 server 是否只是示例、SDK 或嵌入式组件；
- 项目是否停止维护、无法部署或构建证据不足；
- 是否与其他候选属于同一产品的 fork、镜像或重复实现。

未通过负面审查的项目进入拒绝清单，并记录结构化拒绝理由，不得仅从主清单中静默消失。

## 9. 主清单与候补规则

除 50 项主清单外，维护至少 15 个完成同等证据核验、评分和负面审查的有序候补项目。

只有以下情况允许递补：

- clone 经过规定重试后仍失败，且确认仓库不可获取；
- 固定 commit 不存在或不可获取；
- CodeQL 建库经过规定构建和 JDK 尝试后仍失败；
- 建库期间发现入口、权限、依赖或 server 形态证据不成立；
- 实际源码证明项目不满足硬门槛。

递补后仍须满足最终 50 项、旧 Top-50 重合不超过 10、至少 17 个初始本地不存在的新项目以及所有评分硬门槛。不得为了凑数降低标准。

## 10. 下载与版本固定

对最终清单中初始本地不存在的项目：

1. 使用规范 `owner/repo` 和大小写归一化 slug 去重；
2. 记录筛选时默认分支 HEAD commit；
3. 浅克隆默认分支并 checkout 固定 commit；必要时按 commit 增量 fetch；
4. 存放到 `frameworks/applications/<owner>__<repo>/`；
5. 核对 checkout HEAD 与清单固定 commit 一致；
6. 不修改、移动或删除任何已有源码目录；
7. 若新清单包含超过 17 个本地缺失项目，则全部下载并尝试建库。

fork、镜像和更名仓库按上游产品归并，只保留主要维护仓库。

## 11. CodeQL 数据库准备

### 11.1 路径

继续使用当前路径约定：

```text
源码：frameworks/applications/<owner>__<repo>/
数据库：databases/applications/<owner>__<repo>-db/
```

每个数据库先写入本轮独立临时目录。验证通过后才能原子移动到最终路径。不得覆盖已有有效数据库；已有数据库若属于新主清单，则先验证并复用。验证失败时记录异常，不自动删除或替换。

### 11.2 构建策略

按以下顺序尝试：

1. 官方 Maven/Gradle wrapper 和官方文档所示 server 模块；
2. 系统 Maven/Gradle 的等价模块构建；
3. 项目专属、受控的 build override；
4. CodeQL autobuild；
5. 只有确有必要时才使用 bounded `javac` 采集。

JDK 根据项目元数据选择，通常尝试 17、21、22；项目明确要求 Java 8 或 11 时使用本机可用兼容 JDK，否则记录环境缺口。

bounded `javac` 或允许编译失败仅能作为有限覆盖手段。此类数据库必须标记 `coverage_status: limited`，不能与正常 Maven/Gradle build-mode 提取混为一谈。主清单优先保留完整构建项目；有限覆盖显著影响审计价值时使用候补替换。

### 11.3 数据库成功条件

数据库只有同时满足以下条件才算成功：

- `codeql database create` 返回成功；
- 存在 `codeql-database.yml`；
- 存在非空 `db-java/`；
- 数据库已经 finalise；
- 通过当前 CodeQL CLI 提供的基础数据库验证；
- 能确认提取结果包含 Java source 或 compilation unit，而不是空壳数据库；
- 记录 CodeQL CLI 版本、JDK、构建命令、server 模块、日志和 coverage 状态。

目录存在或命令曾启动都不能计为成功。

### 11.4 失败、重试与分类

每个项目采用有限重试：

- clone 最多三次并退避；
- 每个兼容 JDK 对正式构建尝试一次；
- 明确的网络依赖解析失败可额外重试一次；
- 对 clone、checkout、磁盘不足、超时、依赖解析、编译、CodeQL 和数据库验证错误分别分类；
- 不通过无限延长超时、`true` 掩盖错误或忽略空数据库制造成功；
- 所有失败保留结构化状态和日志；
- 达到策略上限后仅从已审核候补池递补。

## 12. 资源控制

- CodeQL 建库默认最多两个项目并发；
- 启动前检查可用磁盘和 CodeQL CLI；
- 每个项目设置独立 clone、构建和 CodeQL 超时；
- 只清理本轮创建的临时数据库和临时构建目录；
- 不清理 Maven/Gradle 全局缓存，不触碰旧结果；
- `frameworks/`、`databases/` 和大体积 `results/` 保持本地资产属性，不纳入 Git；
- 构建进程失败或中断时仍要保留状态记录，并清理本轮临时目录。

## 13. 产物

本轮使用版本化产物，避免混入旧 Top-50：

```text
frameworks/2026-07-18-github-java-web-dos-top50.md
intel/applications/java_web_dos_top50_20260718.json
results/application_dbs/dos_top50_20260718/
├── discovery_candidates.jsonl
├── reviewed_candidates.jsonl
├── rejected_candidates.jsonl
├── reserve_candidates.jsonl
├── selected_targets.json
├── overlap_report.md
├── status.jsonl
├── summary.md
└── logs/
```

含义如下：

- `discovery_candidates.jsonl`：两个发现通道得到的原始候选；
- `reviewed_candidates.jsonl`：完成证据核验和评分的候选；
- `rejected_candidates.jsonl`：拒绝项目及结构化理由；
- `reserve_candidates.jsonl`：至少 15 个有序候补；
- `selected_targets.json`：最终 50 项机器可读清单；
- `overlap_report.md`：与旧 Top-50 和初始 183 项快照的重合统计；
- `status.jsonl`：clone、checkout、构建、验证和递补事件；
- `summary.md`：最终人类可读结果。

机器可读主清单和 Markdown 清单必须由同一结构化数据生成或相互校验，避免两个清单漂移。

## 14. 自动验证

清单形成后自动检查：

1. 项目数恰好为 50；
2. slug 大小写归一化后无重复；
3. 与旧 Top-50 重合不超过 10；
4. 至少 17 项不在初始 183 项快照中；
5. 每项都有固定 commit；
6. 每项有官方默认部署入口证据；
7. 每项依赖数为 0–3；
8. 每项有普通低权限可达性说明；
9. 每项有具体资源耗尽机制和负面审查结论；
10. 每项满足总分和分项硬门槛；
11. 主清单和候补池不重叠；
12. 旧清单、初始 183 项快照和本轮候选均可追溯。

建库后自动检查：

- 最终 50 项都有源码目录；
- 所有本轮新增源码均 checkout 到记录的 commit；
- 每项均有有效 Java CodeQL 数据库；
- 数据库路径与 slug 一致；
- 数据库可被当前 CodeQL CLI 打开和验证；
- 每项记录完整或有限 coverage 状态；
- 不把失败、空数据库或仅创建目录计为成功；
- 至少 17 个初始不存在的项目完成 clone 和建库。

## 15. 人工抽查

至少人工复核：

- 所有从旧 Top-50 保留的项目；
- 所有本轮新增项目；
- 所有 WebSocket 或 gRPC 项目；
- 所有采用 build override 或有限覆盖的项目；
- 所有总分或硬门槛接近最低值的项目。

抽查重点是默认配置、启动文档、监听地址、依赖数量、权限模型、具体资源耗尽机制及其反证。

## 16. 测试与质量门

实现阶段应为清单解析、归一化、评分硬门槛、重合约束、初始快照判定、候补递补、数据库结构验证和状态汇总增加自动测试。

至少覆盖以下失败场景：

- 第 51 个项目或少于 50 项；
- 旧 Top-50 重合达到 11 项；
- 初始本地不存在项目少于 17 项；
- 重复 slug、fork 或镜像；
- 缺少固定 commit 或官方入口证据；
- 依赖数量超过三个；
- 低权限门槛或资源耗尽门槛不足；
- 候补与主清单重叠；
- CodeQL 命令成功但数据库为空或未 finalise；
- 有限覆盖被错误标记为完整覆盖；
- 构建失败后递补导致全局约束失效。

## 17. 完成定义

只有同时满足以下条件才报告完成：

- 新 Top-50 清单通过全部自动约束和人工抽查；
- 与旧 Top-50 重合不超过 10；
- 至少 17 个初始本地不存在的项目已下载并固定版本；
- 最终 50 项均有通过验证的 Java CodeQL 数据库；
- 失败项目已由完整审核的候补项目递补；
- 所有选择、拒绝、构建和递补过程均有可审计记录；
- 没有删除、移动或覆盖任何旧源码和数据库。

如果 GitHub 限流、仓库下线、磁盘不足、CodeQL 环境或兼容 JDK 阻塞工作，应如实报告未完成项目、现有成功数和具体原因，不得把部分结果描述为完成。
